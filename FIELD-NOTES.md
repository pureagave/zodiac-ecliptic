# Field notes

Things this project learned the hard way, each one measured and then pinned by a
test. The project rule is **measure, don't guess**: when a datasheet, a manual or
a confident bench result disagreed with the hardware, the hardware won.

---

## 1. The GPS filter that starved a parked vehicle (found at Black Rock City)

**Symptom.** On the playa, the hero tablet (taking position from the beacon, with
its own GNSS as fallback) showed `NO FIX` and flipped between sources all day. The log showed 59 round trips:
`NET -> SYSTEM failover`, then `back on NET` while NET was *still* searching.
The tablet was bouncing between two sources that both looked dead.

**Measurement.** `dumpsys location` said the GNSS was fine the whole time: a
3.8 m horizontal accuracy, 34 satellites across four constellations, and a
fix updating at 1 Hz with age ~0 s. The fixes existed; the cockpit wasn't
receiving them.

**Cause.** `SystemLocationSource` asked Android for updates with
`minUpdateDistance = 1 m`. That's a minimum *displacement*: Android holds every
fix back until the device moves that far. A parked vehicle almost never moves
1 m, so only the occasional noise excursion delivered a fix, the freshness check
demoted the source in the gaps, and failover bounced the fleet to a primary that
wasn't there. **Every bench test was done while driving, which hid it
completely.**

**Fix.** Rate-limit on time (1 s), never on distance. A test records what the
source actually asks Android for and was mutation-checked (put `1f` back and
that test alone fails). Verified on the hero at Black Rock City: 59 flaps
before, 0 demotions after.

## 2. The manual said 270°. It's 180°.

The DMX moving-head spotlight's manual gives its tilt range as 270°. Measured,
it is 180°. Believing the manual scaled every tilt command by 1.5× and cost real
hours. While in there, the dimmer turned out to be on channel 8, not channel 5
(which is the colour wheel). Both are pinned by tests that fail if anyone
"corrects" them back to the manual.

## 3. Two hand-written protocol implementations drifted in ten ways

The `ZTHREAT` wire format has a Python producer (the Jetson) and a Kotlin
consumer (the tablets). Neither is authoritative. A differential comparison
found they had silently drifted in **ten measured ways**, including:

- Kotlin's float parser accepts Java *source* syntax, so a hex float like `0x1p3`
  in an azimuth field became a live contact 8° off the bow on the driver's HUD,
  while Python rejected the same frame.
- Python's `int()` accepts underscores, whitespace and unbounded magnitudes, so
  a 4000-digit track id parsed on one side and was dropped on the other.
- `3.5e38` is finite in 64-bit and infinite in 32-bit, so one side kept a contact
  the other discarded.

The fix is a measured **golden corpus** (`protocol/threat-protocol-golden.json`:
111 parse vectors, 27 format vectors) that both test suites read, and both
**fail loudly** if it's missing rather than skipping. It's regenerated by re-running
the differential comparison, never hand-edited.

## 4. The thermal lens's "160°" is the diagonal

FLIR quotes the Lepton Ultra Wide as "160°" without naming the axis. On a 4:3
sensor with an f-theta fisheye, 160° across the *width* would need a ~200°
diagonal, which isn't a real lens. So it's the diagonal, and the true horizontal
half-angle is ±64°, not ±80°. That matters because the field of view feeds
pixel-to-bearing: the wrong reading mis-aims every edge bearing by up to 16°,
about 2.8 m of miss on a person 10 m away, which is exactly where the tracking
light gets pointed.

Settled on geometry first, then **measured**: a target at a true 40.4° read
42.5° on the running rig (the horizontal reading predicts 32.3°). Under
uncertainty the code deliberately takes the *narrower* reading, because
under-claiming coverage costs a little caution while over-claiming produces a
confident all-clear.

## 5. Failover that can't flap

The tablets take position from the network beacon and fall back to their own
GNSS. A half-alive beacon is the worst case: it's healthy for a moment, then not.
So the thresholds are deliberately asymmetric: **drop after 3 s unhealthy,
recover only after 10 s healthy**. A beacon has to prove itself for much longer
than it takes to lose trust.

## 6. A demo default that put fake people on the driver's screen

The threat source can fall back to synthetic contacts for bench demos. It once
did that by merging the demo feed into the real one whenever the real one was
empty, and the demo flag defaulted to `true`. So a genuine, live **all clear**
was replaced by fabricated collision alarms. The flag now has **no default at
all**; production passes `false` explicitly. An empty live feed is a real
all-clear and must never trigger a fallback. Vision state is always shown as
`LIVE`, `DEMO` or `ABSENT`, never hidden.

## 7. "All round the vehicle" from a rig with no cameras

The passenger display's souls card said `SOULS DETECTED — 0 — THERMAL, ALL ROUND
THE VEHICLE` while the Jetson had no cameras plugged in. Its gate checked
*liveness* (the feed was alive) but never *coverage* (it could see nothing). The
driver's surround ring had refused that state for a long time; the riders'
screen was the one surface that never got the rule. Now a live-but-blind rig
drops the card instead of claiming the circle. Verified against the genuinely
blind box.

## 8. An absent sensor says nothing

The beacon phone broadcasts heading and light level when it has them. When the
sensor is missing it emits **nothing**, not `0.0`. A zero is a value, and the
tablets would have used it: a 0° heading or a "pitch dark" reading that auto-dims
the screens. Same rule for audio: only a level and a beat flag leave the phone,
never audio.

## 9. The rider sees the plan, not the build

The passenger art card shows each piece's image as the artist submitted it,
pre-rendered on a laptop into the cockpit's phosphor look (edge detection,
purple where the piece is lit, scanlines). This is baked in rather than done
live, because the passenger tablets' Android version can't run that shader
and the playa has no reliable internet. The trade-off: submissions are often
concept art, so riders see the plan, not always what got built. Photos fetched
after the event and baked in for the next year would fix it.

## 10. A test that cannot fail is worthless

Several of the bugs above shipped with every test green. Some tests simply
agreed with the code they tested: one re-typed a coordinate constant to
"verify" it, so a wrong value would have passed. The tests here now check
against something **outside** the file under test (the bundled survey data, the
city's published geometry, a measured corpus), and the important ones are
mutation-checked: break the code and confirm the test goes red.
